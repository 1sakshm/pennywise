# Decisions log

Running log of what was tried, what changed, and why. Newest at the bottom.

## 2026-10-26

- **Hardware is a 4 GB RTX 3050 laptop GPU, not 8 GB.** The brief sized SFT for 8 GB. Plan: freeze most of the encoder, train the top few ModernBERT layers + Laya's decision head in bf16 with micro-batch + grad accumulation. LoRA stays available as a fallback if that still OOMs.
- **Laya param count is 421M total** (ModernBERT-large ~395M encoder + decision head trained from scratch), per the official model card. The brief's "~395M" refers to the encoder only.
- **venv built from Anaconda Python 3.13** (`D:\Anaconda\python.exe`): the `python` on PATH is MSYS2's (POSIX-layout venvs, no CUDA torch wheels), and the `py` launcher points at a removed 3.11. torch 2.6.0+cu124.
- **Base checkpoint = root `convaiinnovations/laya`** (English, 512 ctx). `laya-typed-decisions` has 1024 ctx but is already specialised to four unrelated workflows; starting from the base keeps the RL story clean.
- **Laya used through its own `load_checkpoint` / `build_sequence` / `collate_items`**, not re-implemented. Our argmax matched `laya.Agent.predict` on 5/5 sample prompts, so the encoding is verified.
- **Triage slice classifies the injected bug type, not the exception type**, because the exception type is printed in the traceback and would make the task trivial. Tracebacks are sanitised to `prog.py` so local temp paths don't leak into the dataset.
- **Grader sandbox on Windows**: `python -I` in a temp dir, a 5 s timeout, a minimal env, and `socket` monkeypatched to raise. There's no OS-level network isolation, which is acceptable because the code under test comes from MBPP and from our own tier models. Sanity check: MBPP references pass 20/20 and injected bugs pass 0/20.
- **Off-the-shelf embedding baseline = `sentence-transformers/all-MiniLM-L6-v2`** (384-d, normalised): one of the most widely used sentence-embedding models, and small enough to also run on CPU at serve time.
- **Cached split forward for SFT/RL.** The bottom 24 of 28 ModernBERT layers are frozen, so their outputs are computed once per prompt and cached. Training runs only the top 4 layers + head. Checked against the full forward: max |Δp| = 0.0045 (bf16), and fwd+bwd is 2.5× faster (176 vs 433 ms per batch of 16).
- **Serving shares frozen weights across λ policies** (`router/serve_policy.py`): base Laya is loaded once, and each λ owns only its trainable modules (stored as fp16 deltas). That's ~1.7 GB + ~0.3 GB per extra λ, instead of 1.7 GB per policy. During cached training the frozen layers are offloaded to CPU in fp32 (this freed ~1.2 GB VRAM: RL had been spilling into shared memory at 3.95/4 GB). Saved checkpoints therefore keep the exact frozen weights.
- **RL keeps best-val weights in RAM** and writes the checkpoint once at the end. Writing an 850 MB checkpoint on every val improvement cost ~20 s per write.
- **Proxy mode → λ mapping is rule-based** (`eval/evaluate.py: choose_modes`): `auto` = the cheapest RL policy whose accuracy isn't significantly below always-large (paired bootstrap); `auto-quality` = the most accurate; `auto-cheap` = the cheapest that's at least as accurate as always-medium. The rules are applied to **val-split** results, never test, so the λ behind each mode is chosen without looking at test numbers.
- **RL activation checkpointing + VRAM cap.** Measured: params + AdamW take 1.14 GB, but activations peaked at 3.52 GB on long-prompt batches. On WDDM that spilled into shared system memory, and steps swung between 0.6 and 3.9 s. Checkpointing the 6 trained layers in `logits_cached` brought the peak to 2.42 GB, and `set_per_process_memory_fraction(0.85)` makes the allocator free its cache instead of spilling. Median step is now ~640 ms.
- **RL steps 1500 → 800, snapshot every 40.** 800 × 16 samples is ~22 passes over the 570 train prompts, which is plenty for a 3-arm contextual bandit initialised from SFT. It's ~11 min per λ instead of ~20, and the 6-λ sweep fits the Mon-evening slot.
- **CPU serving latency (measured on this laptop, RL training running concurrently):** fp32 median 1036 ms at 4 threads and 694 ms at 8 threads. **Int8 dynamic quantization rejected:** quantizing the whole model crashes Laya's head (`nn.TransformerEncoderLayer` fast path). Quantizing only the encoder brought the median to 414 ms but agreed with fp32's argmax on just 37.5% of prompts (max |Δp| 0.51), so it effectively becomes a different policy. Plan: keep fp32, try ONNX Runtime (Laya ships an `onnx` extra) once real checkpoints exist, and pick a deploy host with ≥ 4 dedicated vCPUs. Sticky sessions mean an agent pays the routing cost once per conversation. The site shows measured live latency, not the GPU number.
- **ONNX Runtime for CPU serving: same decisions, 1.5× faster.** The base Laya policy exported with `torch.onnx.export` (opset 17, dynamic batch/length) had argmax agreement 1.0 and max |Δp| 0.0 vs PyTorch. Median latency was 469 vs 714 ms at 8 threads, with RL training running concurrently. Plan for the real checkpoints: a shared lower-layers graph (embeddings + 24 frozen layers, exported once) plus a small per-λ graph (top 4 layers + head). That mirrors the cached training split and avoids storing a full 1.7 GB model per λ. Tool: `scripts/onnx_export.py`.
- **No budget for paid inference → free-tier provider + list-price cost model.** The user has no money for API credits. The options checked: OpenRouter `:free` (50 req/day without a credit purchase), Groq free (~200K tokens/day per model, vs ~650K needed per tier), Cerebras (a card is now required for its trial), and NVIDIA's API (public model list; reported as rate-limited ~40 RPM with no daily cap and no card). We use NVIDIA's API. Actual spend is $0, so each tier's cost is the **public list price of the same model** on a paid provider, recorded in `price_source`. Every reported cost means "what this would cost at list price". `run_models.py` now spaces requests per key (`rpm`).
- **Tiers (NVIDIA free API, all open weights, all with published list prices).** small = `nvidia/nemotron-3.5-lightning-30b-a3b` (32B/3B active, OpenMDW-1.1, $0.07/$0.20), medium = `minimaxai/minimax-m3.1-flash` (220B, MiniMax community licence, $0.15/$0.60), large = `nvidia/nemotron-3-ultra-550b-a55b` (560B, OpenMDW-1.1, $0.60/$2.40). Prices are OpenRouter list prices on 2026-10-26. Selection: 24 models were probed for a tool-call round trip + a math check. Many listed models returned 404 or timed out on the free tier. Nemotron-3.5-Bolt-E4B also worked, but has no published price anywhere, so it was not used (no invented prices).
- **Pilot findings (60 prompts × 3 tiers).** (1) With `max_tokens` 1024, 31 answers were truncated mid-reasoning (these are reasoning-style models), so the cap is now 4096 and truncated rows were re-run on every tier alike. `finish_reason` is now recorded. (2) MiniMax is rate-limited hard on the free tier (429s), so the runner backs off 15–90 s on 429. (3) **GSM8K/ARC/MBPP are saturated:** small 93.3%, medium 100%, large 95.0%. That made routing nearly trivial and flagged the problem per the brief. (4) The ladder isn't monotonic: medium beat large and cost about the same as small per request, because small writes ~3× more output tokens. Lowest price per token ≠ lowest cost per request.
- **Harder dataset mix (user-approved).** 948 prompts: GSM8K 100, **MATH-500 levels 4–5 150**, ARC 100, **MMLU-Pro 200**, MBPP 200, agent bug-fix 98 (half carry **two** injected bugs; longer functions only), agent triage 100 (longer functions). MATH answers are graded on the last `\boxed{}`, with conservative LaTeX normalisation + numeric comparison (`data/graders.py: norm_math`; checks in `tests/test_math_grader.py`). It may under-credit exotic but equivalent forms, and this affects all tiers equally.
